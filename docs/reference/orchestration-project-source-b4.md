# #134 / #116-B4: orchestration task source decision

Decision: **BLOCKED — no approved producer or receipt proof.** Production Project Map remains **Source Unavailable**. A Task belongs to a Run, but that Run has no authoritative Project binding. The existing nested write boundary also cannot certify committed activity. Tests characterize these failures; they do not mint source authority.

Audit base: Draft #133 at `124bd60732331d1273d3627e13f9533fea2f94f1`, stacked on #131 and #129. #130 is the separate design reference. No dependency is merged or approved by this decision. No Run schema, wire contract, DevelopmentEvent v1, production source, consent issuer, IPC, preload, RPC or Corporate egress behavior changes.

| ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

SSH control-plane calls may execute against a client Main while the actual work runs on SSH. Paired runtimes carry foreign namespaces; WSL is a separate execution realm. Neither a local SQLite commit nor a terminal handle proves native-local activity. Missing peer contact remains **unverifiable**, never proof of process exit. Paths, display names, pane strings and payload claims cannot repair the missing link. Worktree movement/deletion/recreation and cross-project or host ID collisions require current authoritative revisions, not string joins or B3 structural snapshots.

## What commits, and what does not

`db/lifecycle-transition.ts:transitionLifecycleWithDb` intentionally opens no transaction. Its guarded UPDATE checks the expected prior state; `changed:true` means one SQL row matched, including same-state updates. It says nothing about outer commit or whether the semantic status changed.

`beginLifecycleWriteTransaction` reserves a writer with `BEGIN IMMEDIATE`, or opens a savepoint if already in a transaction. `commitLifecycleWriteTransaction` executes **COMMIT only for the outer owner**; nested callers merely RELEASE the savepoint. `tasks/task-status-transition.ts:updateTaskStatus` settles Dispatches and promotes dependencies before commit/release. A failure rolls back all those writes. A returned completed row from a nested call can still disappear on outer rollback. An observer in either helper, or immediately after an arbitrary method return, would be unsafe.

| Source path                                       | Meaning of a successful write                                                                                                                                            |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| RPC `messaging/message-methods.ts:taskUpdate`     | Caller-selected status/result, admitted under current Run scope. Main acceptance of a database state; no independent verification of execution outcome.                  |
| `db/dispatch-context/dispatch-context-store.ts`   | Dispatch creation claims the Task under a savepoint and sets dispatched before independent worker-start evidence.                                                        |
| `db/dispatch-context/worker-report-settlement.ts` | Validates active Task/Dispatch ownership and duplicate reports; commits/releases through the nestable lifecycle transaction runner. The outcome remains worker-reported. |
| `db/federation/federation-relay-import.ts`        | Imports a remote report and settles the same Task projection inside its own outer transaction. The final COMMIT is in the importer.                                      |
| `db/legacy/legacy-lifecycle-operation.ts`         | Composes settlement, mailbox and receipt writes; the legacy operation owns final COMMIT.                                                                                 |
| `lifecycle-reconciliation.ts`                     | Builds report-derived Task result JSON. Report body/path/provenance must not be copied into Project Map content.                                                         |

Missing Task and identical status with omitted result are no-op returns. A same-status call with explicit result can write and refresh `completed_at`; it is not a new completion. Conflict recovery may return a concurrent writer's current row. `BEGIN IMMEDIATE` serializes writers before lifecycle reads, while guarded UPDATE rejects stale expected states. A rejected/busy/rolled-back invocation supports no new fact.

The lifecycle graph permits corrections between all six Task statuses; the public updater additionally enforces active Dispatch/worker ownership and requires an active Dispatch for dispatched. Completion can reopen, then complete again. The mutable current row/timestamp has no immutable transition ID or ordinal. Polling it cannot distinguish a duplicate from a second real completion, and cannot reconstruct omitted transitions.

The existing `recordAcceptedReportFact` in `worker-report-settlement.ts` is a real narrower fact producer, not a new storage gap to reimplement blindly. When an optional observation is supplied, it atomically writes minimal accepted outcome/report ID into `attempt_observation_facts`, with immutable ID and per-Dispatch sequence. `attempt-observation-store.ts` rejects conflicting replay and accepts identical replay. These facts remain inside the caller's transaction until outer commit. They attest **accepted worker reports**, not universally new Task transitions: the duplicate settlement branch can append another accepted report ID without changing Task state, direct status updates need no report fact, and remote reports do not become native-local evidence. Task/Dispatch deletion triggers in `create-graph-tables-sql.ts` and orchestration reset remove them. They have no authoritative Project binding or delivery/revocation contract. This existing stream is therefore also BLOCKED for Project Map, but must be considered for reuse in any later fact-storage review.

There is **no existing universal after-commit observation seam**. A future reviewed implementation could insert a sanitized immutable transition fact in the same transaction, then read it through a separate connection after commit. This would need unique fact IDs, monotonic per-binding sequence, accepted origin, immutable binding generation and explicit status-change detection. It is a separate storage decision, not implemented here. A bare after-return callback loses events on crash; an outbox requires reviewed retention, replay/deduplication, deletion and revocation rules. Neither should retain raw results. Current Task retention must not be mistaken for durable activity history.

## DevelopmentEvent v1 decision

| Source fact                               | Mapping decision                                                                                                                                               |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| pending / ready                           | No supported v1 task event.                                                                                                                                    |
| dispatched                                | Reject `task.started`: scheduling/claim does not prove execution began.                                                                                        |
| failed                                    | Reject `task.completed`; v1 has no `task.failed`. Do not substitute `agent.failed`.                                                                            |
| blocked                                   | No supported v1 task event and no independent blocker evidence.                                                                                                |
| A newly committed transition to completed | **Candidate only**, narrowly described as Orchestration Task state completion, after identity, commit and source approval gates. No mapping is authorized now. |
| repeated completed / result-only update   | No new lifecycle event.                                                                                                                                        |
| remote/worker report                      | Assertion provenance remains explicit; local persistence cannot upgrade it to independently verified native-local execution.                                   |

Completion does not establish test success, code correctness, review, human approval, actor ownership or dependency evidence. The Task graph's same-Run dependency checks do not authorize invented DevelopmentEvent relationships. No current mapping is allowed for production. Any future candidate must exclude specification/title derived from specification, result, prompt, transcript, credentials and token-bearing paths/identifiers. Use only approved opaque scoped identifiers and minimal versioned status facts; `source` is a label, not authentication. DevelopmentEvent v1 is unchanged.

## Smallest next implementation task

**Separately review and implement a Main-owned Run source-binding record at trusted Run creation; keep it unavailable until underlying owner evidence exists.** The owner is `runs.ts:runCreate` composition plus `run-create.ts:createRun` storage, not a later Task observer. Persist an opaque binding reference atomically with Run creation only after Main resolves exact Project, ProjectHostSetup, Repo, discriminated git-worktree/folder identity, concrete execution host/realm and installation/runtime namespace from authoritative inventories. Capture monotonic ownership/binding revisions; fence on deletion, moves, replacement, takeover or changed ownership. Coordinator rebind must preserve or explicitly invalidate this identity. A nullable `projectId`, terminal lookup or structural snapshot is insufficient.

The review must choose whether an out-of-workspace Dispatch is excluded or receives its own authoritative attempt binding; current code cannot decide that implicitly. Legacy/unbound/ambiguous/remote records stay unproven without backfill by inference. Folder ownership needs explicit underlying records. Older peers/readers must tolerate the absence of any optional new binding and receive no source eligibility; no new required wire field or opcode is justified. No schema/migration is changed in this PR.

Acceptance for that bounded follow-up: actual Main-created binding; atomic failure leaves no bound Run; project/host mismatch and namespace collision deny; native versus WSL/SSH/paired distinction; stale ownership/takeover invalidates; old/legacy clients remain unavailable. Only after this passes should a separate committed-fact storage proof be considered.

## Verification scope

`orchestration-project-source-facts.test.ts` uses real SQLite connections and production lifecycle methods to characterize visibility, rollback, replay/no-op and rebinding. `orchestration-project-source-report-facts.test.ts` examines the existing accepted-report fact stream's commit/replay limits, without treating report observation inputs as trusted project authority. Existing Task/Dispatch invariant/race tests cover settlement rollback and concurrent writer reservation. B3 identity and B2 registry/lease/admission/availability/revocation suites remain the negative proof for cross-scope, changed bindings, revoked authority, duplicate/stale admission and unavailable production sources. They are **not** an end-to-end source receipt proof.

No receipt implementation exists, so receipt rollback/replay/revocation tests are deliberately deferred rather than satisfied with hand-written trusted authority. Native/Electron/remote/WSL acceptance is not claimed; no app or QA VM needs launching for these test/document changes. Local command results, final SHA and exact-head CI are recorded in the Draft PR and issue updates.
