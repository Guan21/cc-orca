## Actual admission and persistence

`src/main/runtime/rpc/methods/orchestration/runs/runs.ts:orchestration.runCreate` parses only `objective` and `from`. `run-scope.ts:resolveOrchestrationCaller` checks supplied compatibility evidence against a declared handle when verification succeeds, then resolves a stable pane. Compatibility attestation is not required for ordinary unbound creation. A stable pane is a coordination identity, not a Project identity. Caller-added Project, Setup, Repository, realm, revision and binding fields are stripped by the existing Zod schema.

The RPC calls `OrchestrationDb.createRun` in `runtime/orchestration/db/runs/run-create.ts`. It opens `BEGIN IMMEDIATE`, unbinds previous consumers for that pane, inserts the Run, records the coordinator routing handle and executes final `COMMIT`. Any later SQL failure restores the previous consumer and removes the new Run and routing record. It does not nest under a savepoint: an already-open transaction is rejected at BEGIN, leaving the outer transaction owned by its caller. Waiter cancellation and the RPC receipt happen after this final commit.

The persisted Run has objective, coordinator handle/pane, consumer generation, legacy marker, timestamps and `home_database=this_database`. None supplies an exact Project or native-local identity. `runUse` can move coordination to a replacement process/workspace; increasing `consumer_generation` fences consumers, not ownership changes. Direct `createRun` also accepts no Project evidence. Consequently there is no existing trusted binding input to persist atomically.

## Missing producer and why no standalone prerequisite was added

The missing producer belongs at **Main's Run admission composition**, immediately after caller resolution in `runs.ts` and before `db.createRun`. This composition would have to consume the exact execution host's launch/incarnation evidence and a host-qualified checkout/catalog ownership epoch, acquire independently owned native-root evidence, and supply one immutable creation snapshot to the existing final SQLite transaction. The current runtime launch registry, Store catalog and SQLite Run database are separate owners; no existing function composes those facts or makes an ownership authorization decision.

The narrowest tempting prerequisites were checked and rejected:

- **Store ownership counter only:** requires coverage of repo projection, reconciliation/import/removal, independent setups, worktree metadata and host/checkout replacement. A counter in one setter leaves other writers and ABA uncovered. Store `loading-store/write-scheduling.ts` schedules JSON persistence after 1–5 seconds, while `createRun` commits SQLite synchronously. A volatile revision or an independently flushed JSON counter cannot itself establish atomic cross-store ownership or native-root authority after a crash. No crash-safe ownership ledger/issuer currently exists to reuse.
- **Immutable coordinator origin receipt:** can truthfully preserve routing selectors, but cannot satisfy Project ownership, installation or native-root evidence. Adding an inert side table would preserve claims without establishing the missing authority. It was not added as a substitute binding.
- **Lookup at creation or on read:** exact structural equality, local routing defaults, paths, folder groups and user selections do not mint authority; lookup on read also changes historical scope after rebind/move.

These are missing authoritative producers and a durability/composition boundary, not a nullable-field problem. Implementing a new ownership authority across these owners would require decisions outside this narrow source-binding slice. No independently useful safe production prerequisite was established here. **NOT_PROVEN is the actionable result, not a successful binding implementation.**
